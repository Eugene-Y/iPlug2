## 1. T-034: NanoVG GL main-FBO stencil clear (`IGraphics/Drawing/IGraphicsNanoVG.cpp` `DrawResize`)

**Root cause: confirmed.**
- `glnvg__fill` (`nanovg_gl.h:1011`) builds the winding count with INCR_WRAP/DECR_WRAP from whatever is already in
  the stencil. It then covers the bounding quad with `NOTEQUAL 0` and ZERO ops. So a stale non-zero stencil paints
  the bbox, and the first fill re-zeroes that area ("until redrawn").
- `glnvg__convexFill`, non-stencil strokes and text never use the stencil, which matches "strokes, text and convex
  fills unaffected".
- `nvgluCreateFramebuffer` (`nanovg_gl_utils.h`) attaches a new `GL_STENCIL_INDEX8` renderbuffer and never clears it.
- `BeginFrame` clears before `nvgBindFramebuffer(mMainFrameBuffer)`, so it clears the window, not the FBO.
- The layer `Bitmap` constructor (`:118-128`) already clears its FBO. The probe output and
  `evidence/t034/{unfixed,fixed}-first-open-*.png` (looked at) show the claimed result: boxes in 3 of 4 opens without
  the fix, 0 of 5 with it.

**Platforms.**
- **Context:** `ScopedGLContext` at the top of `DrawResize` existed before this change. `nvgCreateFramebuffer` already
  needs a current context there, so the fix adds no new requirement on any platform.
- **GL calls:** `glClearStencil`/`glClear` are GL 1.0 / GLES2 / WebGL1 calls.
- **Clear state:** `glClear` honours the scissor test and the colour/stencil write masks. `glnvg__renderFlush` leaves
  scissor disabled, the colour mask all-true and the stencil mask 0xffffffff, which are also the GL defaults. The
  `Bitmap` constructor relies on the same.
- **GL state left behind:**
  - The viewport is set to the FBO size, the same value `BeginFrame` and `UpdateLayer` set.
  - The clear colour is 0, the same as `BeginFrame`.
  - The stencil clear value is 0, the GL default; nothing else sets it.
- **Metal:** unaffected. The block is under `#ifdef IGRAPHICS_GL`, and `nanovg_mtl.m:928-929` clears the stencil
  with a load action on every pass.
- **Web:** WebGL already zero-initialises renderbuffers, so the clear is redundant there but harmless.
- **Placement:** `DrawResize` is the right place. It is the only place `mMainFrameBuffer` is created, and NanoVG keeps
  the stencil at zero after that. A per-frame stencil clear in `BeginFrame` would also work but is not needed. The
  colour must not be cleared per frame because IGraphics redraws only dirty rects.

| Sev | Where | Finding | Suggested fix |
|---|---|---|---|
| nit | `IGraphicsNanoVG.cpp:516` (hvoya `:510`) | `nvgBindFramebuffer(nullptr)` is now the first `nvgluBindFramebuffer` call in the process, so NanoVG's process-wide static `defaultFBO` is captured here and no longer in the first `BeginFrame`. It also leaves `defaultFBO` bound where `nvgluCreateFramebuffer` had restored the previous binding. On every current backend the window FBO is 0 at that point (GLX, WGL, WebGL, ANGLE/EGL on iOS), and Apple GL rebinds `mInitialFBO` in `EndFrame` anyway, so nothing changes today. | Optional: save `GL_FRAMEBUFFER_BINDING` before the bind and restore it after, so `DrawResize` has no binding side effect. |
| nit | comment `:507-510` | "until something redraws" is really "until a fill covers that area". The comment is otherwise a good WHY. | — |

**Verdict: approve.**

## 2. CLAP `paramsValueToText` off-by-one (hvoya 593293cfb = da7cd2493, `IPlug/CLAP/IPlugCLAP.cpp`)

- The CLAP spec (`clap/ext/params.h:280-284`) names the argument `out_buffer_capacity` and requires a
  null-terminated string. `strcpy` writes `GetLength()+1` bytes.
- The old guard `size < len` let `size == len` through, writing one byte past the buffer. The new guard
  `size <= (uint32_t) len` is exact. The cast is safe because `GetLength() >= 0`.

| Sev | Where | Finding | Suggested fix |

| nit | `IPlugCLAP.cpp:539` (hvoya) | Returning `false` when the buffer is too small leaves the host with no text. Truncating would be friendlier, but `false` is spec-conformant. | Optional: truncate with `strncpy` plus a terminator. |

## 6. Gneiss master ecda56a, b1733b7; Sand master d2294da

- **ecda56a (dangling `initializer_list`): claim verified.** A minimal repro of the old pattern
  (`const std::initializer_list<const char*> l = c ? std::initializer_list<…>{…} : std::initializer_list<…>{…};`)
  built with GCC 13 `-fsanitize=address` reports **stack-use-after-scope** when `l` is read. The rewritten pattern
  (named lists, `c ? a : b`) is clean under the same flags. GCC gives no warning at `-Wall -Wextra`. Clang and MSVC
  put such constant arrays in static storage, so they never showed it.
  - Whether C++17's elision through `?:` should extend the array's lifetime is arguable. The new code is correct under
    any reading, since both arrays live for the whole function.
  - No other `? std::initializer_list` remains in Gneiss, Sand or `hvoya/` utils.
- **b1733b7:** a function-local (even `static constexpr`) used in a lambda's default argument is ill-formed
  ([dcl.fct.default]: a local variable may not appear as a potentially-evaluated expression). GCC is right and clang
  is lax.
  - Moving the constants to file scope is correct. Namespace-scope `constexpr` has internal linkage, so no clash with
    other translation units.
  - `PLUG_INFO_HEADER_HEIGHT` comes from `config.h` and was already used at file scope (`:27`).
  - No other `boundsPad`/`headerH` in the file.
- **d2294da:** `std::isfinite` with `<cmath>` included (`svf_zdf.hpp:4`) is the portable spelling. libstdc++ does not
  guarantee a global `::isfinite`.
